## Summary

`podnext copy` / `podnext sync` expand sparse files to their dense size. A 10 MB sparse file with zero allocated blocks grows to ~11 MB of real disk after a sync. The copy reads and writes every logical byte and never detects holes.

## Reproduction

```sh
# inside container: create a sparse file, then sync it out
truncate -s 10M /tmp/sparse.bin
stat -c '%s bytes, %b blocks' /tmp/sparse.bin    # 10485760 bytes, 0 blocks
podnext sync c1:/tmp/ /tmp/out
stat -c '%s bytes, %b blocks' /tmp/out/sparse.bin # dense allocation
```

## Evidence: observed log

```
task-3 (power-user validation) reported:
  - Sparse files: no hole detection (`SEEK_HOLE`). 10MB sparse file (0 blocks allocated)
    expanded to 11MB dense physical allocation during sync.
```

## Root cause

`cmd_copy` and `cmd_sync` in `crates/podnext/src/main.rs` stream content. They do not use `lseek(SEEK_DATA/SEEK_HOLE)` hole mapping or `copy_file_range`.

## Impact

- Disk amplification occurs for any image or workspace that uses sparse files, such as VM disk images and database files. On a phone this is a real capacity cost.

## Proposed fix

Detect holes with `SEEK_DATA`/`SEEK_HOLE` and re-create them with `ftruncate` + positional writes, or use `copy_file_range` where the platform supports it.
