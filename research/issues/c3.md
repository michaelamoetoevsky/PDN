## Summary

`podnext reset <name>` **deletes the container directory first and downloads the base image
afterwards**. If the command cannot fetch the image reference, the download fails. That failure
occurs *after* the destruction of the existing container. The data loss is permanent and
unrecoverable.

The normal lifecycle reaches this defect. `backup restore` records the **source container name**
in `metadata.json["image"]`. That value is not a registry reference. A later `reset` of that
restored container tries to pull a local container name from Docker Hub. The pull gets `401
Unauthorized`. By then the container of the user is already gone.

## Reproduction

```sh
podnext backup create deb-pdn
podnext backup restore <id> --name deb-copy   # writes image = "deb-pdn" into metadata
podnext reset deb-copy
# Resetting 'deb-copy' from 'deb-pdn'.
# This deletes the container and everything inside it.
# <container dir removed here>
# Error: registry returned 401 Unauthorized for 'deb-pdn'   <-- too late
```

## Evidence from the observed log

```
task-3 (power-user validation) reported:
  Critical Bug (`podnext reset` on restored containers):
  `podnext backup restore` writes the source container name into `metadata.json["image"]`.
  Calling `podnext reset` attempts to fetch that local name from Docker Hub
  (`401 Unauthorized`), destroying the container before verifying download availability.
```

## Root cause

`crates/podnext/src/main.rs:3116`

```rust
println!("Resetting '{}' from '{}'.", name, image_ref);
std::fs::remove_dir_all(&container_dir)?;                 // destroy FIRST
install_image_native(&image_ref, &name, false, None).await?;  // download SECOND
```

The destructive step runs before any proof that the image is obtainable. Also, the recorded
`image` can be a value that is not a registry reference.

## Impact

- The container contents suffer irreversible loss on any network failure, registry failure or
  authentication failure.
- The failure is silent. The tool tells the user that the reset occurs, then the user has nothing.

## Proposed fix

1. On restore, persist the **original OCI reference**, `debian:13`, in metadata. Do not persist
   the source container name.
2. Resolve and verify the image with a manifest fetch **before** any operation on the existing
   container. Extract to a staging directory and swap only on success. A failed download then
   leaves the original container intact.
