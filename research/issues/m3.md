## Summary

A deeply nested archive inside a container extracts slowly. The time scales super-linearly with depth and **times out past ~200 levels**. Every path operation in the guest costs a traced syscall through PRoot's ptrace loop.

## Reproduction

```sh
podnext run alpine -- /bin/sh -c '
  cd /tmp && mkdir -p deep && cd deep
  for i in $(seq 1 200); do mkdir -p d$i && cd d$i; done
  cd /tmp && tar -cf deep.tar deep && time tar -xf deep.tar -C out'
```

Measured wall time for unpack vs depth:

| Depth | Time |
|-------|------|
| 10    | 1.07 s |
| 30    | 1.61 s |
| 60    | 4.93 s |
| 100   | 15.48 s |
| 150   | 50.43 s |
| 200   | timeout (>60 s) |

## Evidence: observed log

```
Depth 10:  code=0, time=1.07s
Depth 60:  code=0, time=4.93s
Depth 100: code=0, time=15.48s
Depth 150: code=0, time=50.43s
Depth 200: TIMEOUT >60s
proot info: vpid 1: terminated with signal 15
```

## Root cause

The system traps each guest `openat`/`mkdirat` and resolves its path in user space. The cost for each syscall grows with path length, and deep trees multiply the number of syscalls. This is inherent to the ptrace backend rather than a bug in PDN's extractor.

## Impact

- Legitimately deep source trees are slow or unusable. Examples are node_modules nesting and Java package trees.
- A user who hits a timeout sees a truncated extraction with no clear cause.

## Proposed fix

- Document the ptrace scaling characteristic and recommend bounded archive depth.
- Raise the default command timeout for extraction-heavy operations.
- Longer term, offer the UML backend for extraction-heavy work. It uses a real guest kernel, where syscall cost is native.
