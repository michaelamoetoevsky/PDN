## Summary

Concurrent writes to the **same file inside the same container** clobber each other. In the test, 4 of 5 workers read back another worker's data. Container-level locking exists, but it protects only metadata operations, not the guest filesystem. Two `podnext run` invocations that target one container therefore race freely.

## Reproduction

```python
# 5 threads, same container, each writes its own token to the same shared path,
# then reads it back and compares.
# Worker 0: expected token_0, read 'token_0', clobbered=False
# Worker 1: expected token_1, read 'token_0', clobbered=True
# Worker 2: expected token_2, read 'token_0', clobbered=True
# Worker 3: expected token_3, read 'token_0', clobbered=True
# Worker 4: expected token_4, read 'token_1', clobbered=True
# Total clobbered: 4/5
```

## Evidence: observed log

```
task-2 (race conditions) reported:
  Worker 0: expected token_0, read 'token_0', clobbered=False
  Worker 1: expected token_1, read 'token_0', clobbered=True
  ...
  Total clobbered: 4/5
```

## Root cause

`ContainerLock` serializes registry-style operations, but `run` and `login` do not acquire it for the duration of guest execution. Nothing arbitrates concurrent guest processes that write the same path. The guest sees a normal shared filesystem.

## Impact

- Silent data corruption for any workload that assumes exclusive access.
- Users reasonably expect container-level isolation to extend to concurrent invocations.

## Proposed fix

Decide and document the contract. Option a: allow concurrent `run`, and document it as a shared filesystem with POSIX semantics and no guarantee. Option b: acquire an advisory lock for each container for the execution window. Option a is cheaper and matches container semantics. Either way, remove the dead "locking exists, so we are safe" assumption. State the real behavior in the docs. Add the clobber test to the suite to pin the chosen contract.
