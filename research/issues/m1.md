## Summary

`podnext ps` reports **no sessions** while containers run. Only the interactive `login` path writes session records. The non-interactive `run` path never registers a session, so `ps` shows an empty table even with N running workloads.

## Reproduction

```sh
podnext run alpine -- sleep 10 &
podnext run alpine -- sleep 10 &
sleep 1
podnext ps
# +----+-----------+------+---------+-----+-----+--------+---------+---------+
# | ID | CONTAINER | USER | COMMAND | CWD | PID | STATUS | CREATED | STARTED |
# +----+-----------+------+---------+-----+-----+--------+---------+---------+
# (empty — two workloads are running)
```

## Evidence: observed log

```
task-2 (recursive/stress) reported:
  === PODNEXT PS DURING CONCURRENT RUNS ===   -> empty table
  === PODNEXT PS DURING CONCURRENT LOGINS === -> empty table
  CLI bug: `cmd_run` never invokes `register_session`.
```

## Root cause

`crates/proot-distro-core/src/session.rs:41` defines `register_session`, and `crates/podnext/src/main.rs` calls it only on the interactive login path. The `cmd_run` path executes the container without a session record, so `active_sessions()` finds nothing to probe.

## Impact

- Operational blind spot: no way to observe running non-interactive workloads.
- The JSON/table split compounds it. That split is reported separately: the table reads disk and the JSON reads in-memory state.

## Proposed fix

Register a session record in the `run` path as well, and release it on exit. Or unify both paths behind one execution entry point that always registers. Add a test that asserts `ps` sees a `run` workload while that workload is alive.
